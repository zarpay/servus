# Servus 1.0.0 — part two: events, generators, and a demo app

Follow-up to the first 1.0 note. Everything below landed after it, so nothing
here repeats. Same PR: https://github.com/zarpay/servus/pull/54

## Event invocation is always asynchronous

An Event class chose its own execution mode per declaration, and synchronous
was the default. A sync reaction ran inline inside the *emitting* service's
`after_call`, before its result reached the caller.

That is backwards. It meant a follow-up with nothing to do with the caller
could slow their request down, and an exception in that follow-up propagated
out of a service that had already succeeded. Events exist to decouple; reacting
synchronously re-couples the reaction's latency and failure to the emitter.

The docs already carried a "prefer async invocation" warning. This makes it the
behaviour.

## `invoke` is now `enqueue`

Renaming follows from the above: the method no longer invokes anything, it
enqueues. Keeping the old name would leave the DSL describing something the
code stopped doing.

```ruby
# before
invoke Ledger::RecordEntry::Service, async: true do |payload|
  { amount: payload[:transferred] }
end

# after
enqueue Ledger::RecordEntry::Service do |payload|
  { amount: payload[:transferred] }
end
```

The `async:` option is gone — both `async: true` and `async: false` now raise.
Rejecting `async: false` is the point: it asked for synchronous invocation,
which no longer exists, and silently giving it the opposite would be worse than
refusing.

The migration is a chain of errors, each naming the next step:

```
`invoke` was renamed to `enqueue` in 1.0.0 — event invocation is always
asynchronous. Replace `invoke` with `enqueue`, and drop `async:` if present.

`async:` is no longer a valid option — event invocation is always
asynchronous. Remove it from the declaration.
```

**This makes events a Rails-only feature for now.** Reactions run through
ActiveJob, so an Event class that declares `enqueue` needs it. Without it you
get a named error rather than the bare `NoMethodError` you used to. Servus's
core — services, schemas, guards, the bus itself — still works without Rails. A
job adapter for other hosts comes later.

## Generated services declare a schema

`rails g servus:service` used to emit a commented-out schema block, which meant
the common path was a service with no contract — the opposite of what this
release argues for. It is now live code:

```ruby
schema(
  arguments: {
    type: 'object',
    required: %w[from_account gold_dragons],
    properties: {
      from_account: {},
      gold_dragons: {}
    }
  },
  result: { type: 'object', required: [], properties: {} }
)
```

The generator fills in what it can know — every parameter is required — and
leaves what it cannot as an empty schema, with a TODO. Guessing `type: 'string'`
for every parameter would have been worse than saying nothing: an id is an
integer, a model is an object, and a generated service that raises on first
call because the scaffold asserted something false is a bad first experience.

So a fresh service enforces argument presence and nothing more until someone
types it.

## A demo app

New in the repo: `demo/`, a Rails app that uses every feature of the gem, with
every file annotated as a textbook. 200 examples, 95% coverage, and CI runs it
on every PR.

It path-pins the gem source, so it is an integration test — a change that
regresses documented behaviour fails there even when the gem's unit suite
passes. It is also the reference: when the docs describe a feature abstractly,
the demo shows it running, with commentary on why it is written that way.

`demo/README.md` has a reading order mapping each feature to the file that
teaches it. If you want to see anything in this release working, start there.

Building it found six real problems in the gem, which is rather the point.

## What this means for core

**The event migration is the big one, and bigger than the first note implied.**

92 `invoke` declarations. Only 14 are already async. **77 are synchronous and
will start running in jobs.**

That is not a rename. For those 77, the emitting service will no longer wait
for the reaction and no longer fail when the reaction fails. Anything that
quietly depended on that ordering — a reaction that had to finish before the
response went out — was a step in the service rather than a reaction to it, and
needs to move there.

I would treat that review as the main task, well ahead of the mechanical
rename. Find them with:

```bash
grep -rn 'invoke ' app/events/ engines/*/app/events/
```

Our `SubscriptionRouter` also merges an `async` flag into the Invocation
options hash. That flag is now meaningless, so the router needs a look
regardless.

Two things that are *not* problems for us. We already run
`require_event_payload_schema = true`, and I checked: all 29 emitted event
names resolve to a registered Event class, so the new enforcement finds nothing.
And the generator change is forward-only — it affects services generated from
now on, not the 476 we have.

## Findings worth knowing

Six things the demo surfaced, in rough order of how much they would cost you.

**The `async` DSL is unusable in development.** `ActiveJob::Base` is lazily
autoloaded, so the railtie hook has not fired when a service class body runs,
and `async queue: :critical` dies with `NoMethodError`. It works in production
and under RSpec, failing only in `console` and `runner`. Works everywhere you
test, fails where you debug.

**A service returning nil instead of a Response blames the wrong file.** It
fails with `undefined method 'success?' for nil` raised from inside Servus's
logger, pointing at the logger rather than at the service that forgot to
return.

**`call_async` silently eats reserved arguments.** A service argument named
`queue`, `wait`, `wait_until`, `priority`, or `job_options` is taken as a
scheduling option and removed, so the service never receives it and fails its
own schema later, inside the job.

I grepped us for this. One hit — `ContentHub::UpsertVideo` takes
`option :priority` — and it is latent rather than live: nothing calls that
service asynchronously or enqueues it from an event today, so it works fine.
It would break the moment someone does, which is exactly the kind of tripwire
worth knowing about before you trip it.

**A generated `ServiceJob` constant is not a file**, so referencing it before
its service has loaded raises `NameError`. Eager loading hides this in
production; it bites in specs.

**`log_filter_parameters` does not cover event payloads.** Service arguments
are masked, payloads are not — so a secret placed in a payload is logged in
clear. Relevant to us given what moves through our events.

**The service generator's spec template is stale**, referencing three things
that do not exist. The service file it generates is fine; the spec file is not.

The first and last are arguably 1.0 blockers rather than follow-ups, since 1.0
is the release people will read generator output from. Opinions welcome.
